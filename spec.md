# OctoDeck Specification

**Current Status:** Functional pre-alpha. Core Go daemon, local SQLite caching, embedded React Web App dashboard, Chrome Companion Extension, and release automation pipeline are operational.

---

## 1. High-Level Architecture

* **The Backend (Daemon):** A local Go server (`octodeck serve`) that handles business logic, GitHub API interactions, and local persistence. It listens on `127.0.0.1:38274` and embeds the React Web App UI static files directly via `//go:embed frontend_dist`. Its runtime version is dynamically extracted from git tags and injected at build time via `-ldflags` into `server.Version`, surfaced through the CLI (`octodeck --version`) and the HTTP `/api/v1/status` endpoint.
* **The Web App Dashboard:** Hosted exclusively by the Go backend daemon at `http://127.0.0.1:38274/`. Renders the maintainer triage interface using ConnectRPC over relative `/api/v1` routes with SameSite Anti-CSRF cookies (`octodeck_csrf`), surfacing the daemon runtime version in the settings modal.
* **The Companion Extension:** A lightweight Manifest V3 Chrome Extension. Manifest V3 metadata is injected at build time with numeric and descriptive SemVer versions. Handles browser-native capabilities (`github.com` view tracking, GitHub action tracking & auto-sync, desktop notifications and toolbar badge pushed by the daemon, action toolbar launcher, GitHub right sidebar integration with Ack/Star/Notes controls, and grouped timeline noise collapsing). Displays daemon pairing, version status, and version mismatch warnings directly in its options page.
* **Release Automation & Quality Gates:** A repository-level release and verification pipeline that enforces Conventional Commits and backtick restrictions via Git hooks (`.githooks/`), generates categorized Markdown release notes from commit history (`scripts/release-notes.sh`), and manages strictly incremental SemVer releases (`release.sh`) protected by full verification preflights (`./verify.sh --force`).

## 2. Component Architecture

### 2.1 The Backend Daemon (`octodeck`)

- **API Gateway:** Serves ConnectRPC endpoints over HTTP/1.1 at `http://127.0.0.1:38274/api/v1`, wrapped with a global logging interceptor.
- **Static File Server:** Native embed (`//go:embed frontend_dist`) serving the compiled Web App UI (or fallback placeholder when uncompiled) at `/`.
- **Version Management & Health Endpoint:** Reads dynamic build-time git versions injected via `-ldflags` into `server.Version` (falling back to `"dev"`), exposed via the CLI root version flag (`octodeck --version`) and the `/api/v1/status` HTTP health endpoint alongside GitHub authentication status.
- **Data Store:** Local SQLite database (`~/.octodeck/octodeck.db`) using **Hybrid Storage** (Smart Index + Protobuf Blob).
- **Logging & Error Interception:** Structured JSON logging (`slog`) to Stdout. A ConnectRPC logging interceptor wraps unary and streaming handlers, automatically logging procedure errors via `slog.ErrorContext` with structured attributes (`procedure`, `code`, `error`, and HTTP `request_id`).
- **Auth Manager:** Uses `go-gh` for GitHub authentication and handles companion token authorization. The authenticated user's login is resolved once at daemon startup and cached by the GitHub client, which is the single source of truth read by request handlers and the sync engine; requests never look it up from GitHub. If startup resolution fails (e.g. offline), each sync run retries it until it succeeds. The cache is refreshed by every successful live auth check (`/api/v1/status`), which is also the only place the client reloads `gh` credentials, so a changed identity is picked up without per-request lookups.
- **Status Calculator (`logic/status_calculator.go`, `logic/activity.go`):** Derives single status from underlying independent activity flags (`ComputeActivity`: item, mention, comment, code, noise) in strict priority order (1. Never before seen: "New" — or "New Mention" if explicitly mentioned, 2. Explicit `@mention` of the authenticated user in new comments or PR reviews: "New Mention", 3. New non-noise comments, PR reviews, or human state events by others: "New Activity", 4. New commits by others: "New Commit", 5. New noise comments, bot reviews or review comments, or bot state events: "Noise", 6. Idle: no display, plus "Acked") based on the effective last-viewed time, the acknowledgement watermark, user identity, and configured known bots. Activity after the later of the effective last-viewed time and the watermark is new. Unsubmitted (pending) PR reviews are not activity: they are dropped at GitHub ingestion and ignored by the calculator and timeline.
- **Structured Query Engine (`internal/query/`):** Evaluates boolean expression trees (`Expr`: `and`, `or`, `not`, and `Predicate` of field, ORed values, and negation) over the vocabulary defined by the `Field` enum in `api/octodeck/v1/query.proto` (design: `docs/internal/query_model_design.md`). Validates every request (known fields, non-empty values, legal values for closed fields), rejecting bad trees with `InvalidArgument` and an `ExprError` detail giving the path to the offending node. Expands `triage:all` to `inbox,acked`, resolves `@me`, and ANDs an implicit `triage:inbox` onto the root when no `triage` predicate appears anywhere in the tree. Evaluation is in memory against items with computed `new:` activity flags; free text (`FIELD_TEXT`) matches title and body as case-insensitive substrings, ANDs separate terms, matches `123`/`#123` against the item number, and is narrowed by `in:title`/`in:body`. `GetItems` first loads candidates through an SQL prefilter translated from the SQL-expressible part of the tree (indexed `repo`, `author_login COLLATE NOCASE`, `state`, `type`); the prefilter may return extra rows but never drops a match, falls back to a full scan when the translation would be too deep or the SQL query fails, and a conformance test asserts identical results with and without it. `GetFacets` counts every known value of each requested field over the query with that field's own top-level predicates removed (`triage` falls back to `triage:all`)—accumulating total `count`, `new_count` (`new:any`), and `inbox_count` (`triage:inbox`) per value, plus universe-level `latest_activity_at`, `total_count`, and 30-day `recent_count` for `FIELD_REPO`—and evaluates additional `queries` (for saved-search counts) in the same pass with per-query error reporting, feeding selector dropdowns and all sidebar counts. Sorting puts starred items first, then the requested key (latest non-noise activity, ack time, or creation time).
- **Effective Last-Viewed Time (`logic/viewed_state.go`, `frontend/src/logic/viewState.ts`):** The user has necessarily seen an item up to their own latest activity on it, regardless of whether auto-ack is enabled. The effective last-viewed time is the later of `last_viewed_at` and the user's latest own activity (authoring the item, commenting, submitting reviews or review comments, pushing commits, or performing state events). The Status Calculator uses it as the viewed baseline, so own activity never counts as unviewed activity: an item the user opened or acted on is never "New", only activity by others after the user's latest action surfaces, and commits authored by the user never trigger "New Commit" (commits by others or without a linked GitHub login do). The daemon exposes it on read as the server-computed `ItemLocalState.computed_last_viewed_at` (alongside `computed_status`; recomputed on every read and never a source of truth). The dashboard Details Pane and the extension's timeline markers place the "Last Viewed" divider by it, so the divider never sits before the user's own latest activity; the extension holds the view time from page arrival (so recording the visit doesn't hide what was new) but still raises it to own activity reported while on the page.
- **Acknowledgement Model (`ItemLocalState`, `logic/ack_state.go`, `frontend/src/logic/ackState.ts`):** An item's acknowledgement is two timestamps. `acked_at` is when the ack happened (daemon wall clock for explicit acks; the user's own GitHub event time for auto-acks); its presence marks the item as acked and it drives "Last Acked" ordering. `acked_activity_at` is the activity watermark on GitHub's clock: activity at or before it is acknowledged. An explicit ack sets the watermark to the newest synced activity timestamp the calculator inspects (updated/created time, comments, submitted reviews and review comments, commits, state events), never the wall clock, so activity that happened on GitHub but has not synced is not hidden. Readers fall back to `acked_at` when `acked_activity_at` is unset. An acked item stays "Acked" until newer non-noise activity by someone else arrives; the user's own comments, reviews, commits, and state events never un-ack it (commits by others, including maintainers and bots, or by authors not linked to a GitHub account, still do). Bot comments, slash commands, bot reviews and review comments (unless they @mention the user), and bot-performed state events are noise. Un-acking clears both fields. Both backend helpers and the shared frontend helpers (used by the dashboard Details Pane dividers, "Last Acked" sorting, and the extension's timeline markers and sidebar) apply the fallback; timeline dividers compare against the watermark and the effective last-viewed time at whole-second precision.
- **Noise Filter:** Classifies comments on read into `CommentNoiseType` (bot authors, slash commands) without storing transient noise state in the database.
- **Bot Discovery:** During sync, actors that GitHub reports as `Bot` (the GraphQL `__typename` of authors and actors, mapped to `USER_TYPE_BOT`) or whose logins match bot naming patterns are added to the configured known bots. The authenticated user is never added.
- **Auto-Ack Engine:** When `auto_ack_own_activity` is enabled, sync automatically acknowledges items whose latest significant event was performed by the current user. Opening the item counts as an event, so an item the user opened is acknowledged at its creation time until someone else acts on it. Significance uses the same predicates as the Status Calculator, so noise (bot comments, slash commands, bot reviews and review comments, bot state events) never blocks auto-ack; commits and pending reviews are ignored. It runs whatever the item's current status: whenever the user's event is newer than the current watermark it advances `acked_activity_at` to that event's time and sets `acked_at` to the same time unless an existing `acked_at` is later. Neither field ever moves backwards.
- **Sync Engine:** Orchestrates notification-first data synchronization; cold start inventory sync seeds the working set by combining recent notifications with open authored/assigned search queries.
  - **Hydration:** Uses GitHub REST notifications with `If-Modified-Since` for HTTP 304 fast exits, filters excluded repositories before hydration, resolves unknown items to GraphQL Node IDs (`ResolveNodeIDs`), and hydrates items in batches of up to 50 (`FetchItems`), including assignment events (to un-ack on assignment) and `SubscriptionState`.
  - **Notification backfill window:** Each notification fetch pages up to a safety cap (20 pages / 1000 threads). Because GitHub returns threads newest first, a capped incremental fetch records the unfetched range (from its `since` to just past the oldest fetched thread) as a persisted backfill window (metadata `notification_backfill_window`) before advancing the cursor. Every later sync drains the window with GitHub's `before` parameter (no conditional request), shrinking it when the drain is itself capped and clearing it once fetched completely. Forced syncs reach back to the previous cursor so they never skip threads.
  - **Comment gap backfill:** Backfills issue comments when stored history is disconnected from the hydrated page.
  - **PR review backfill:** Pages backwards from the newest review (`FetchReviews`, up to 500 reviews) when the hydrated reviews page reports older reviews that do not connect to stored history. At most 10 backfills run per sync cycle; deferred or failed backfills persist a pending marker (`ItemLocalState.review_backfill_before`) and are retried when the item is next re-hydrated or by a throttled end-of-cycle sweep that spends the cycle's remaining budget on pending items.
  - **Review comment completion:** Review comments live on their parent `Review`, with `reply_to_id` as the thread ID. Remaining comments are paged (`FetchReviewComments`) only while the stored copy is incomplete, and a review paged to exhaustion is not re-paged until GitHub's comment count changes.
  - **Error capture:** Records per-item `sync_error` in `ItemLocalState` without aborting sync.
- **Trace Store & Observability:** Records structured sync traces (`sync_traces` table) capturing query parameters, duration, item counts, errors, HTTP status, reasons breakdown, and gzipped raw payloads (`sync_traces.raw_payload_compressed`) with automatic 24-hour retention pruning during garbage collection. Accessible via `octodeck debug traces`, `octodeck debug trace [id]`, and the Web App Debug Data Browser UI.
- **Discovery Engine & Auxiliary Search Queries:** Periodically discovers candidate items matching configured GitHub search queries (`tracked_queries`) without continuous polling overhead. Automatically injects an `updated:>` filter into searches referencing the last run timestamp minus a safety buffer (2 minutes) to account for GitHub indexing latency. Newly added queries are seeded with the query creation timestamp in SQLite metadata to avoid expensive historical backfills. Configuration validation rejects queries with explicit `updated` qualifiers and enforces at least one positive scope qualifier (`repo:owner/name`, `org:name`, or `user:name`). On save (`UpdateConfig`), newly added queries undergo a per-query 48-hour pre-flight check (`CountSearchIssues` with `created:>`) that returns warnings if a query exceeds an average of 50 newly created items per day unless confirmed (`force_save`). Executes lightweight GraphQL search queries (`SearchCandidates`, sorted `sort:updated-asc`, replacing any `sort:` qualifier in the query) returning matching Issue and PullRequest node IDs with their update times, following the search cursor for up to 5 pages (500 results) per query per run. A query's discovery cursor (and its yield statistics) only advance after the run's new candidates are hydrated and stored: to the search start time when the search completed, or to the newest update reached when it stopped at the page cap, so the next run resumes there (which also keeps each search under GitHub's 1000-result limit); a failed hydration leaves every cursor in place. Discards previously known items via an in-memory $O(1)$ deduplication check against the SQLite item index (`GetAllItemIDs`) before issuing any hydration calls. Newly discovered candidate items are batch-hydrated (`FetchItemsByIDs`) with their full details and `viewerSubscription` state. For queries present in `auto_subscribe_queries`, newly discovered unsubscribed items are automatically subscribed on GitHub (`UpdateSubscription` with `SUBSCRIBED`) when the `notifications` OAuth scope is available, falling back gracefully to unsubscribed persistence on error.
- **Untracked Item Lifecycle & GC Refresh:** Discovered unsubscribed items are persisted in SQLite with their initial snapshot state and remain dormant without continuous notification polling. Stale unsubscribed open items (including those with an unknown subscription state) are refreshed after 7 days during the daily garbage collection pass, while other open items are refreshed after 30 days. The discovery engine is dynamically scheduled via a dedicated discovery ticker (`discovery_interval_min`, default 10 minutes) that resets upon configuration reloads.
- **Subscription Mutation API:** The `UpdateSubscription` ConnectRPC handler executes the GitHub GraphQL `updateSubscription` mutation to alter subscription state on GitHub (`SUBSCRIBED`, `UNSUBSCRIBED`, `IGNORED`) and updates the local SQLite item state, recalculating computed status and returning the updated item. It detects missing GitHub OAuth scopes (specifically the `notifications` scope) or organization SAML enforcement and maps them to an actionable `connect.CodePermissionDenied` error directing the user to run `gh auth refresh -s notifications`.
- **Config Manager:** Loads configuration from `~/.octodeck/config.json` with atomic write-backs. Single source of truth for known bots, repository/label filter patterns, sidebar repository sort mode (`repo_sort_mode`: alphabetical, recent 30-day activity, or total cached items), saved searches (`saved_searches`, stored as raw query text and optional sort in display order), tracked auxiliary search queries (`tracked_queries`), per-query auto-subscribe preferences (`auto_subscribe_queries`), discovery interval (`discovery_interval_min`), sync intervals, auto-ack preferences, and notification/badge settings (`notification_settings`). Saved searches are normalized on load (assigning missing or duplicate IDs and repairing names) and mutated through dedicated by-id read-modify-write RPCs; `UpdateConfig` rejects `saved_searches` in its field mask and preserves the stored list on unmasked updates. Any `pinned_repos` entries present on load or update are automatically converted into `repo:owner/name` saved searches and cleared (writing a one-time `config.json.bak-pinned-repos` backup when converting on load). Scalar defaults (intervals, port, auto-ack, `repo_sort_mode`) are applied on load and after every update, so clearing a field via the update mask behaves like a reload; notification setting defaults are applied on read and never written to disk.
- **Notification Engine (`logic/notifications.go`, `logic/sync_notifications.go`, `internal/notify/`):** The daemon decides desktop notifications and the toolbar badge; the extension only displays them. Notifications are not persisted: they are decided when sync reconciles a freshly fetched item against its stored copy (reconciliation is serialized so concurrent syncs of the same item notify once) and published only after the merged items are saved. An item notifies when it is new (category "New") or has new activity by others since the stored latest activity (categorized like the Status Calculator: Mention, Activity, Commit; bot commits and comments are Noise and never notify), filtered by `notification_settings` (enabled, repo/label/author include/exclude patterns, only assigned-or-authored, ignore bots, new items/new activity toggles, with mentions optionally bypassing the filters). Events are timed by when they became visible (a review comment by the later of its creation and its review's submission), and history older than the stored latest activity never notifies. A first-seen item only notifies if it was created, or has activity, within the last 24 hours. Nothing notifies while the database is empty (the cold-start inventory sync, which is retried each scheduled tick until it populates the database). Each notification carries a dashboard deep link (`?item=`). The badge is computed from local state per `badge_count_mode` (Inbox, Unread, or Disabled) by a single debounced loop shared by all subscribers (retried with a warning on failure), invalidated when sync saves items, local state is mutated (view/ack/star/subscription/delete), or config changes.
  - **Broadcaster (`internal/notify/`):** An in-memory fan-out of notifications and badge changes to `WatchNotifications` subscribers, retaining a ring buffer (500 entries, 24 hours) for catch-up. Each publish (one sync batch) is queued to a subscriber as a single entry; a subscriber that falls too far behind is terminated with `Unavailable` and recovers through catch-up on reconnect. The buffer does not survive a daemon restart, so reconnecting after a restart (or without a cursor) yields no catch-up.
  - **Catch-up & bursts:** A reconnecting client sends the `sent_at` of the last message it received (`last_received_at`). Buffered notifications after it, and live bursts, are reduced to the latest per item; up to 3 are sent individually and more collapse into one summary linking to the dashboard Inbox.

### 2.2 The Frontend (Web App & Companion Extension)

- **Web App Dashboard (`frontend/src/`)**: Full-screen maintainer triage dashboard (Inbox, Details, Settings). Uses relative `/api/v1` routes, URL search parameters for filter state synchronization, `localStorage` for UI layout preferences, and a React `ThemeProvider` supporting GitHub-inspired Light, Dark, and System appearance modes.
  - **Daemon Version Surfacing (`frontend/src/Settings.tsx`)**: Surfaces the backend daemon version (retrieved via `/api/v1/status` with build-time fallback) directly in the Settings modal footer.
  - **Settings Modal Controls (`frontend/src/Settings.tsx`)**: Provides configuration controls for sidebar repository sorting (`repo_sort_mode`: Alphabetical, Recent Activity, or Total Items), `tracked_queries` (with an `"Auto-subscribe on discover"` checkbox in the Add/Edit Tracked Query modal and a read-only `Bell` indicator on auto-subscribe query rows, disabled with a remediation notice when `has_notifications_scope` is false), and `discovery_interval_min` (numeric input under Advanced settings, default 10 minutes, minimum 1 minute) with validation (enforcing `repo:`, `org:`, or `user:` scope qualifiers and rejecting manual `updated:` filters), a pre-flight confirmation prompt (`Save Anyway` / `Edit Query`) when a query exceeds 50 newly created items/day over 48h, dirty-checking, and discard confirmation.
  - **Keyboard Navigation & Action Shortcuts (`frontend/src/hooks/useKeyboardNavigation.ts`, `frontend/src/components/KeyboardShortcutsModal.tsx`)**: Single-key maintainer triage (`j`/`k` or arrows to move list focus, `/` to focus the query input, `Enter` to open Details Pane for focused item, `x`/`e` to Ack with smooth exit transition and auto-advance focus/details, `s` to Star/Unstar, `o` to Open on GitHub in new tab, `Esc` to close details/clear focus, and `?` to toggle keyboard shortcuts modal cheat sheet with sidebar shortcut trigger), guarded against active text inputs and modifier keys.
  - **Card Quick Actions & Smooth Transitions (`frontend/src/components/PullRequestCard.tsx`, `frontend/src/index.css`)**: Subtle hover-disclosed Check action button positioned outside the top-right of cards with fluid 280ms height collapse exit transitions upon dismissal.
  - **Floating Toast Notification System (`frontend/src/context/ToastContext.tsx`, `frontend/src/components/Toast.tsx`)**: Global toast notification system (`ToastProvider`, `useToast`) rendering floating alerts in the bottom-right viewport for user actions and failed mutations (subscribing, acking, starring, settings). Features manual dismiss controls, hover-pausing auto-dismiss timers (8000ms for errors, 5000ms for standard notices), accessible roles (`role="alert"` / `aria-live`), and interactive copyable remediation command buttons (e.g. for `gh auth refresh -s notifications`) with temporary copy confirmation.
  - **Untracked Indicators & One-Click Subscribe (`frontend/src/components/PullRequestCard.tsx`, `frontend/src/components/DetailsPane.tsx`)**: Displays interactive subscription indicators for items where `viewer_subscription` is `UNSUBSCRIBED`. On `PullRequestCard`, renders a compact `BellOff` icon button in the action row between the computed activity status indicator and the hover-disclosed Ack button (with the compact tooltip `"Untracked"`), transitioning to an inline spinning `RefreshCw` icon during in-flight subscription mutations. On `DetailsPane`, renders a full "Untracked" text badge with the explanatory tooltip `"Not subscribed on GitHub. Live updates won't be received automatically unless you subscribe or are mentioned."`. Both indicators trigger the `UpdateSubscription` mutation on click to subscribe the user on GitHub and locally promote the item, and automatically disable with an explanatory remediation tooltip (`gh auth refresh -s notifications`) when the GitHub `notifications` OAuth scope is missing (`has_notifications_scope: false`).
  - **Live Synchronization & Real-Time Updates (`frontend/src/components/Dashboard.tsx`, `frontend/src/components/SyncStatusDisplay.tsx`)**: Periodic polling of daemon sync progress (~2000ms `getSyncStatus`) and dashboard data (~3000ms `getItems` plus two `getFacets` calls: one filtered call for selector dropdown counts and one unfiltered call for all sidebar workflow, repository, and saved-search counts), immediate refetch triggers on sync transition (`isSyncing: false`) or timestamp changes, and live navigation bar indicator & hovercard metrics reflecting background sync in real time.
  - **Viewport Scroll Anchoring & In-View Animations (`frontend/src/hooks/useScrollAnchoring.ts`)**: Layout-aware viewport anchoring preserving the exact visual scroll position without jumping when items insert above the current scroll offset, coupled with smooth CSS grid/transform entry animations for newly inserted in-view items.
  - **Theme System (`frontend/src/context/ThemeContext.tsx`)**: Theme context providing `'system' | 'light' | 'dark'` options, dynamic OS color scheme change listener (`prefers-color-scheme`), `.dark`/`.light` HTML class sync, and `octodeck_theme` local storage persistence.
  - **Structured Query Filter Model & Highlighted Query Input (`frontend/src/logic/query/`, `frontend/src/hooks/useDashboardFilters.ts`, `frontend/src/hooks/useDashboardData.ts`, `frontend/src/hooks/useQueryField.ts`, `frontend/src/hooks/useQuerySuggestions.ts`, `frontend/src/components/query/`, `frontend/src/components/dashboard/`)**: Filter state is the query text (`DashboardQueryState.text`) plus sort (`sort`, `order`) and the selected item (`item`), synchronized with the URL via `?q=`, `sort`, `order`, and `item` (with per-field URL parameters normalized into `?q=` on load). The query syntax module (`logic/query/syntax/` over the field table in `logic/query/vocabulary.ts`) scans, parses, validates, and formats clauses (`key:v1,v2` OR lists, `-key:v` negation, `is:` shorthands, `@me`, quoted values with `\"` and `\\` escapes, `#123` item numbers, `in:title`/`in:body` text scopes, and free-text terms). The list header mounts the highlighted `QueryInput` (`components/query/{QueryInput,SuggestionList}.tsx`, `components/query/queryInputStyles.ts`, `hooks/useQueryField.ts`): a native auto-growing `<textarea>` owns the query text, caret, selection, undo/redo, IME and clipboard, with transparent glyphs over an aria-hidden decoration layer that wraps identically and draws a tinted pill exactly on each clause (blue qualifiers, rose negations, red errors with a wavy underline on the offending key or value, dashed amber incomplete clauses, neutral free-text terms; colour only, never font weight or strikethrough). Both layers share font metrics with kerning and ligatures off, so focus only cross-fades pill borders (every pill keeps the same fill; bordered at rest, and only the caret's clause bordered while editing) and no glyph ever moves. Gutters between clauses come from CSS word spacing; the textarea shows a display form (`logic/query/displayText.ts`) in which spaces inside quoted values are U+2005 and hyphens are U+2011 (one-for-one substitutions, so offsets are unchanged and lines wrap only between clauses), every read maps back to plain text, and edits that would leave a non-canonical display form are planned in `beforeinput` and applied as single native edits so browser undo keeps working. The field grows line by line up to four lines and then scrolls, Enter never inserts a newline, and pasted newlines become spaces. At rest, hovering a pill with the mouse reveals an inset remove `×` over its trailing glyphs (`logic/query/fieldGeometry.ts`); it never appears while the field is focused and never takes focus. A `×` clear button empties the whole query. The input also provides live key, `is:` shorthand, closed-set value, and `GetFacets`-backed open-field value autocomplete at the caret (`useQuerySuggestions`). The filter controls—triage tab (`Inbox`/`New`/`Acked`/`All`), `State` segmented switch (`All`/`Open`/`Closed`), and right-aligned toolbar selectors ordered `Type` (`Pull requests`/`Issues`), multi-select `Author` (with pinned `@<login> (you)` writing `@me`), `Assigned` toggle, multi-select `Label`, multi-select `Repository` (grouped by organization with mutually exclusive org vs. repo selection), and `Activity` (`Subscribed`/`Unsubscribed` tracking options and a multi-select `New Activity` section), alongside the `...` overflow menu (`OverflowFilterMenu`) housing multi-select `Assignee` and `Milestone` flyouts with progressive right-to-left collapse via `useToolbarCollapse` (`Activity` moving into the overflow menu first, followed by `Repository`)—are a projection (`projectClauses`) of the parsed clauses with owner indices; each control splices (`logic/query/textEdit.ts`) only the clause(s) it owns in the query text while preserving all other clauses and user spelling. Multi-select menus (`MultiSelectMenu`, `useStableOptions`, `useMenuGroup`) display live facet counts, client-side filter boxes, and stable option ordering while open. `useDashboardFilters` debounces typing edits (200ms) while applying control edits immediately, and `useDashboardData` compiles valid clauses into an `Expr` for `GetItems` and `GetFacets` (with no client-side filtering) while excluding invalid or incomplete clauses and reporting diagnostics inline (`resolveQueryErrors`). A selected item outside the current result (deep links, notifications) is fetched with `GetItem`. The DataBrowser requests `triage:all` to show every stored item.
  - **Saved Searches (`frontend/src/logic/savedSearches.ts`, `frontend/src/hooks/useSavedSearches.ts`, `frontend/src/components/savedSearches/`)**: Named dashboard queries stored in `config.json` and surfaced in the sidebar's **Pinned** section between the Inbox/Acked rows and Repositories. An inset pin button inside the query input frame to the left of the clear `×` button (`PinButton` in `QueryInput`) opens `SaveSearchModal`—which embeds a highlighted `QueryInput` with autocomplete alongside a live `GetItems`-backed preview of the matching item count, `SortMenu`, and top 3 matching items—to pin the current query and sort (defaulting the name to the repository name for single-repo queries), or to edit, delete, update in place (**Update**), or fork (**Save as new**) an active or modified pinned search. Each sidebar row (`SavedSearchList`) displays a triage-scope-aware badge (`inbox`, `new`, `acked`, or `all`) derived from the single unfiltered sidebar `GetFacets` call's `counts` (or an error indicator when a hand-edited query has syntax or server validation errors). Opening an unscoped saved search preserves the active triage tab's clauses, whereas a scoped saved search replaces the full query; both apply the saved sort, and clicking the active row resets to the current tab's clauses and default sort. Sidebar edit mode (`SavedSearchEditRow`) provides a per-row edit button that opens `SaveSearchModal` in edit mode, deletion with confirmation, and optimistic drag-and-drop or keyboard (`ArrowUp`/`ArrowDown`) reordering with screen-reader live-region announcements.
  - **PR Review Thread Expansion & Timestamp Links (`frontend/src/components/DetailsPane.tsx`, `frontend/src/logic/timeline.ts`)**: Renders clickable external GitHub timestamp links on PR review comments and provides an interactive in-place `view thread` / `hide thread` toggle on review comment replies. Review comments live on their parent `Review` with `reply_to_id` identifying the thread root, and thread context is assembled on demand (`getThreadContext`) by scanning `item.reviews[].comments[]` when a thread is expanded, rendering a `"view full thread on GitHub"` link when the root comment is missing.
- **Companion Extension (`frontend/src/extension/`)**: Manifest V3 Chrome companion extension.
  - **Build-Time Version Injection (`frontend/vite.config.ts`, `frontend/src/extension/manifest.json`)**: Build tooling populates Manifest V3 with a strictly numeric `version` (e.g. `0.2.0`) and full descriptive `version_name` (e.g. `v0.2.0-2-g2c64b7a-dirty`), providing the `__APP_VERSION__` global definition across extension runtime code.
  - **`background.ts` & `notificationStream.ts`**: Holds a `WatchNotifications` server stream to the daemon (bearer-token authenticated, exponential reconnect backoff 1s–30s, a 1-minute watchdog alarm ensured on every worker start, and reconnects on startup/install/token change). The last `sent_at` cursor is kept in `chrome.storage.session` after each message and in `chrome.storage.local` at most once a minute and after every message that showed a notification, so reconnects resume with daemon catch-up without repeating notifications. Shows daemon-pushed desktop notifications and summaries (`chrome.notifications`, deduplicated per browser session, click opens the deep link, restricted to the dashboard origin) and sets the toolbar badge from daemon badge updates, overriding it with `!` when the daemon is unreachable, `SETUP` when unpaired, and `UPD` (with a long retry backoff) when the daemon doesn't implement the notification stream (mismatched versions). Also provides the action click launcher (focuses/opens dashboard tab), daemon liveness checking (10s request timeouts), and known bots caching/synchronization (`chrome.storage.local`). Messages go through a table-driven router (`background/router.ts`) that classifies the sender (GitHub content script vs extension page), allows each message type only from its permitted context, and validates payloads (item operations, notification settings via `GetConfig`/`UpdateConfig` with a `notification_settings` field mask, diagnostics). The toolbar action is rendered from one state (`background/action.ts`): daemon states take precedence, and a degraded GitHub integration turns the badge amber while keeping the count.
  - **`content.ts` & `content/` (GitHub DOM engine, `docs/internal/extension_dom_engine_design.md`)**: A layered engine that keeps GitHub integration working across markup changes and never corrupts the page.
    - **Variants and DOM contract (`content/variants/`, `content/dom/`):** GitHub markup stacks (classic Rails, React) are variant modules that contribute per-scope detectors (page, timeline, sidebar, composer), per-anchor locators and small behavioral adapters. The resolver detects the variant per scope, resolves anchors with declared cardinality (more than one match for a single anchor is ambiguous and fails closed), never returns OctoDeck nodes, and reports fallback selector use as drift. Only `variants/` contains GitHub selectors.
    - **Capabilities (`content/capabilities/`):** The API features use instead of selectors: page facts (kind, identity validated against the URL), whole timeline items with rows and kinds derived from GitHub's GraphQL node-id typename (structural badge icons as fallback), hidden content, GitHub's native "Load more" controls with insertion points for adjacent OctoDeck UI, and bounded sequential loading through GitHub's own controls, anchor lookup and reveal, composer and sidebar insertion points, navigation (scroll/highlight, a progress toast with an optional action button) and user-action classification.
    - **Engine (`content/engine/`):** Page sessions driven by merged navigation signals (Navigation API, Turbo, popstate, hashchange, head observer), a settle window before declaring a scope unrecognized, a feature host that isolates every feature (per-mount AbortController, guarded callbacks, circuit breaker on errors or re-injection loops, recognition gate for mutating features), one shared scoped mutation observer, a typed per-session event bus, and a mutation ledger through which all page changes are made and reverted. Boot hygiene and an instance token prevent duplicate instances after updates; an orphaned script shuts down into a CSS safe mode (`html[data-octodeck-safe]`) that restores GitHub's rendering.
    - **Features (`content/features/`):** View tracking (a view counts after 3s of the tab being visible and focused), action tracking with debounced item refetch, the OctoDeck sidebar section (Ack/Star/Notes, Hide events, and a "Limited" chip when features are degraded), the composer Ack button, noise collapsing (bot and slash-command comments into dense rows; reviews with comments are never collapsed; Hide events hides only allowlisted bodiless event and commit rows), Last Viewed / Acknowledged timeline markers, Expand all (a "Load all" button inline next to GitHub's own timeline "Load more" control, on variants with a verified loader; loads hidden ranges in bounded batches while a top-of-page toast shows progress with a Cancel button) and anchor navigation repair (loads until a linked comment exists, then scrolls to and highlights it). Bot classification on the page is local only (known bots, login patterns, GitHub's "Bot" badge and GitHub App authors; the signed-in viewer is never a bot); the extension never writes to the known bots list.
    - **Diagnostics:** Features report per-session outcomes and drift (anchor, variant, resolution, sanitized structural fingerprint, GitHub release) via `REPORT_DIAGNOSTIC`. The background aggregates health per feature and variant (degraded after repeated failures across distinct pages) and keeps bounded drift records (`background/diagnostics.ts`).
  - **`options.html` & `options.ts`**: Options page for daemon connection status, pairing, and editing the daemon's `notification_settings` (badge count mode, enable toggle, repos/labels/authors wildcard patterns with `!` excludes and inline validation, mentions bypass, assigned/authored, bot ignore, and new item/new activity toggles; disabled with a notice while the daemon is unreachable), displaying extension version and daemon version side-by-side, rendering an alert banner when versions mismatch, and a GitHub compatibility panel (feature health, drift records with Copy report / Download JSON / Clear, and a Safe mode switch).

### 2.3 Release Automation & Contribution Standards

- **Git Hooks (`.githooks/commit-msg`, `.githooks/pre-commit`)**: Version-controlled repository hooks configured via `git config core.hooksPath .githooks`. The `commit-msg` hook enforces Conventional Commits (`type(scope)!: description`) across allowed types (`feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`) and strictly prohibits backtick characters across all non-comment lines to prevent shell injection hazards and release notes Markdown formatting corruption. The `pre-commit` hook invokes `./verify.sh` on changed files prior to commit creation.
- **Contribution Standards (`CONTRIBUTING.md`)**: Comprehensive developer standards documenting development prerequisites, repository setup, git hook configuration, verification procedures, conventional commit formatting, backtick restrictions, release note categorization, and contribution workflow.
- **Automated Release Notes Generator (`scripts/release-notes.sh`)**: Analyzes git commit history between revisions (`git log $PREV_TAG..HEAD`), automatically categorizing commit subjects into Markdown sections: `### Features` for `feat`, `### Fixes` for `fix`, and `### Other Changes` for all other commit types.
- **Release Automation (`release.sh`)**: Orchestrates the release lifecycle with end-to-end preflights:
  - **SemVer Validation**: Validates target version format (`vX.Y.Z` or `X.Y.Z`, normalized to `vX.Y.Z`).
  - **Strict Incrementalism**: Enforces that target versions increment strictly by patch (`+1`), minor (`+1.0`), or major (`+1.0.0`) from the latest git tag, rejecting arbitrary jumps. In tagless repositories, initial releases are restricted to `v0.0.1`, `v0.1.0`, or `v1.0.0`.
  - **Git Preflights**: Enforces execution on branch `main` and verifies a clean working directory with zero uncommitted or untracked changes.
  - **Release Notes Preview**: Generates and displays release notes preview via `scripts/release-notes.sh`.
  - **Verification Gate**: Executes `./verify.sh --force`, aborting release creation if any test, linter, or build check fails.
  - **Tagging & Publishing**: Creates an annotated git tag (`git tag -a <version> -m "Release <version>"`) and pushes the tag to the remote origin repository.
- **GitHub Actions Release Pipeline (`.github/workflows/release.yml`)**: Automated CI/CD release workflow triggered by pushing a version tag (`v*`). Builds the Web App UI, compiles the Go backend binary (`dist/octodeck-<version>-linux-amd64`), packages the companion extension (`dist/octodeck-extension-<version>.zip`) and standalone web app assets (`dist/octodeck-webapp-<version>.zip`), generates commit-based release notes via `scripts/release-notes.sh`, and publishes an authenticated draft release with assets attached via the GitHub CLI.

## 3. Backend API Specification

The backend exposes a ConnectRPC API alongside HTTP REST endpoints. See `api/octodeck/v1/service.proto` for the full schema and contracts.

### 3.1 Services

* **OctoDeckService (ConnectRPC over HTTP/1.1 at `/api/v1`)**
  * `GetItems`: Dashboard items matching a structured `Expr` query (implicitly scoped to `triage:inbox` unless the query has a `triage` predicate), ordered by a separate `Sort`. Invalid queries return `InvalidArgument` with an `ExprError` detail.
  * `GetFacets`: Per-field value counts (`count`, `new_count`, and `inbox_count`) for the requested fields, each computed with that field's own top-level predicates removed (returning every known value, including zero counts), plus `counts` (`CountResult` with `count`, `new_count`, `inbox_count`, or per-query `ExprError`) for any additional `queries` in the request.
  * `GetItem`: Single item retrieval by ID (`owner/repo#number`) with computed status and local metadata.
  * `Sync`: Streaming status updates.
  * `ViewItem`: Record item view timestamp and recalculate item status.
  * `AckItem`: Mutate acknowledged state.
  * `StarItem`: Mutate starred state.
  * `SetNotes`: Update maintainer private notes for an item.
  * `RefetchItem`: Force single item re-fetch.
  * `DeleteItem`: Remove item from local store.
  * `UpdateSubscription`: Update item subscription state on GitHub and in local storage with actionable OAuth scope error remediation.
  * `GetSyncStatus`: Retrieve synchronization status metrics (last successful sync, last update received, failure details, sync duration, 24h/7d/30d notification rates, and `has_notifications_scope` OAuth capability).
  * `GetDatabaseStats`: Retrieve database and storage metrics over all stored items (total items, open/closed, PRs/issues, inbox/acked where acked means a currently computed "Acked" status, repo count, trace count, database size on disk, and file path).
  * `GetConfig`: Retrieve current backend configuration, authenticated `current_user_login`, and per-query discovery statistics (`query_stats` with trailing 7-day and 30-day daily averages).
  * `UpdateConfig`: Update backend configuration, running 48-hour `created:>` pre-flight volume checks on newly added tracked queries unless `force_save` is set. Supports partial updates via `FieldMask` (excluding `saved_searches`).
  * `CreateSavedSearch`, `UpdateSavedSearch`, `DeleteSavedSearch`, `ReorderSavedSearches`: Atomic by-id read-modify-write mutations of `config.saved_searches` returning the updated list.
  * `WatchNotifications`: Long-lived server stream (exempt from the request timeout) of daemon-decided notifications, catch-up summaries, badge updates (deduplicated), and heartbeats (every 20s). Every message carries a `sent_at` cursor that clients echo back as `last_received_at` on reconnect to receive catch-up. The stream ends cleanly on daemon shutdown.

* **Configuration Model (`Config`)**
  * Configurable daemon settings managed via `GetConfig` and `UpdateConfig`, including repository filters (`watched_repos`, `excluded_repos`), sidebar repository sort mode (`repo_sort_mode`), saved searches (`saved_searches`), label filters (`included_labels`, `excluded_labels`), auxiliary search queries (`tracked_queries`) and per-query auto-subscribe preferences (`auto_subscribe_queries`), discovery check interval (`discovery_interval_min`, default 10 min), notification polling interval (`polling_interval_min`), bot account definitions (`known_bots`), auto-acknowledgement preferences (`auto_ack_own_activity`), desktop notification and badge preferences (`notification_settings`: enabled, repo/label/author include/exclude patterns, `always_include_mentions`, `only_assigned_or_authored`, `ignore_bots`, `notify_on_new_items`, `notify_on_new_activity`, and `badge_count_mode`; all toggles default on and the badge defaults to Inbox), server port, and database path.

### 3.2 HTTP REST & Utility Endpoints

* `GET /api/v1/status`: Returns daemon health, GitHub authentication state, `has_notifications_scope` OAuth status, and runtime `version` string.
* `POST /api/v1/auth/companion-token`: Authorizes and creates companion extension authentication tokens.
* `GET /auth/authorize`, `POST /auth/approve`, `POST /auth/token`: OAuth authorization flow endpoints for companion extension pairing.
* `GET /*`: Serves embedded static Web App assets (or fallback placeholder) with SPA routing fallback.
